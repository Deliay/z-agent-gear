# GitHub Issues 联动工作流强制 Worktree 隔离

**功能名称**: GitHub Issues 联动工作流强制 Worktree 隔离
**PRD 版本**: v1.1
**创建日期**: 2026-10-26
**作者**: ZeroAsh Agent

> v1.1 变更：按评审意见，将「工作区主分支信息缺失时快速失败」改为「自动识别并回填主分支」——GitHub 项目通过平台 GitHub 授权获取仓库主分支并记录；其他项目按 main → master → release 顺序探测本地仓库中第一个存在的分支作为主分支；仅当完全无法识别主分支时，本次触发才明确失败。该识别能力同时修复平台内既有「主分支信息缺失即无法实例化」的历史问题。

## 背景与目标

### 1.1 背景

云电脑 GitHub Issues 联动能力（见 [[20261025-github-issues-workflow]]）上线后，用户在仓库中为 Issue 打上联动标签，即可自动完成「工作区准备 → 实例化工作流 → Issue 回评 → 首个人类节点自动完成」的全链路。

但该链路存在一个严重缺陷：**通过 Issues 联动触发的工作流没有启用 Worktree 隔离**。平台内手工实例化工作流时，用户可以勾选「为工作流创建独立 Worktree」；而 Issues 联动通道全程无人工干预，没有任何环节开启隔离，导致：

1. 工作流的所有节点会话直接在**工作区主分支**上执行，AI 的改动直接落在主分支上，污染仓库的基线代码；
2. 同一仓库多个 Issue 并发触发多条工作流时，所有工作流共享同一个主分支工作区，产物相互覆盖、相互串扰；
3. 与手工实例化可选隔离的行为不一致，用户对「联动触发的工作流在哪里跑」没有预期。

此外存在一个相关的历史问题：工作区的「主分支」信息目前依赖人工设置，一旦缺失，需要隔离能力的工作流要么直接失败、要么静默失去隔离，用户只能手工补齐后重试。

### 1.2 目标

- Issues 联动触发的工作流**一律在独立 Worktree 中执行**，每个工作流实例拥有自己独立的工作副本与分支，工作区主分支在整个执行期间零改动。
- 对用户**零配置成本**：联动配置的维护方式不变，无需新增任何选项，触发即隔离。
- 工作区主分支信息缺失时，系统**自动识别并回填主分支**（GitHub 项目经平台授权通道获取；其他项目按常见主分支名顺序探测），用户无需手工设置；仅当完全无法识别主分支时，触发才**明确失败并给出可读原因**，绝不静默降级为在主分支上执行。

### 1.3 成功标准

- 为联动仓库的 Issue 打上触发标签后，自动创建的工作流实例拥有独立的 Worktree 工作副本与独立分支，实例内所有节点会话均在该副本中工作。
- 工作流从触发到执行完毕，工作区主分支不产生任何新提交与未提交改动。
- 同一仓库多个 Issue 并发触发时，各工作流实例互不影响，产物不串扰。
- 工作区未记录主分支信息时：GitHub 项目能自动获取并记录仓库主分支；非 GitHub 项目能按 main → master → release 顺序自动探测到第一个存在的分支并记录；识别后主分支信息对工作区持久可见，后续不再重复探测。
- 仅当主分支完全无法识别（非 Git 仓库或上述候选均不存在）时，触发以失败终态结束，原因在平台中可查看、可追溯；不会出现在主分支上「跑了一半」的情况。
- 手工实例化工作流的「为工作流创建独立 Worktree」选项行为保持不变；手工实例化遇到主分支信息缺失时同样自动识别，不再直接失败（历史问题修复）。
- 未配置联动的云电脑行为与现状完全一致，无回归。

## 用户分析

### 2.1 目标用户

- **云电脑使用者（联动配置者）**：为云电脑配置 Issues 联动，期望 Issue 触发的工作流安全、隔离地执行，不破坏仓库主分支。
- **工作流观察者**：从 Issue 评论进入工作流查看进展，期望看到的是一条干净、独立的执行线。
- **仓库维护者**：仓库主分支需要保持干净可信，不接受自动化流程直接向主分支写入。

### 2.2 用户场景

| 场景 | 用户角色 | 目标 | 痛点 |
|--|--|--|--|
| Issue 触发工作流安全执行 | 云电脑使用者 | 打标签触发工作流，AI 在隔离副本中工作 | 联动工作流直接改主分支，基线被污染 |
| 多 Issue 并发触发 | 云电脑使用者 | 多个 Issue 各自触发的工作流互不干扰 | 共享主分支工作区，产物相互覆盖 |
| 查看工作流执行位置 | 工作流观察者 | 明确知道该工作流实例在哪个副本/分支上执行 | 无隔离时无法区分，改动去向不明 |
| 主分支信息缺失自动识别 | 云电脑使用者 | 无需手工设置主分支，系统自动识别并记住 | 缺失即失败或静默失去隔离，需手工补齐重试 |
| 隔离确实无法建立时感知 | 云电脑使用者 | 触发失败能看到明确原因，便于修复重试 | 静默跑在主分支上，事后才发现 |
| 手工实例化行为不变 | 云电脑使用者 | 平台内手工实例化的隔离选项语义保持现状 | 修复不影响既有手工入口 |

## 功能需求

### 3.1 功能概述

修复 Issues 联动触发链路：为联动触发的工作流实例**强制启用 Worktree 隔离**——实例化时自动为工作流创建独立 Worktree 工作副本，实例内所有节点会话默认在该副本中执行。当工作区缺失主分支信息时，系统先**自动识别并回填主分支**（GitHub 项目经平台授权获取，其他项目按 main → master → release 顺序探测），识别成功则继续建立隔离；仅当主分支完全无法识别、或隔离副本建立失败时，本次触发才以明确原因失败，不降级到主分支执行。该主分支自动识别能力同时覆盖平台内手工实例化路径，修复「主分支信息缺失即失败/静默失去隔离」的历史问题。

### 3.2 功能列表

#### 功能点 1: 联动触发的工作流强制 Worktree 隔离

- **描述**: 通过 Issues 联动触发而创建的工作流实例，无需任何人工勾选，自动获得独立的 Worktree 工作副本与分支；实例内所有节点会话（包括未单独配置隔离的节点）都在该副本中工作，工作区主分支全程不被触碰。
- **用户价值**: 主分支始终干净可信；多条联动工作流并发执行互不干扰；与「Issue 驱动开发」的心智模型一致——每个 Issue 对应一条独立的改动线。
- **验收标准**:
  - [ ] 为联动仓库 Issue 打上触发标签后，自动创建的工作流实例持有独立 Worktree 副本与分支，且实例详情中可看到该分支信息
  - [ ] 工作流全部节点执行过程中产生的文件改动只出现在该实例的 Worktree 副本中，工作区主分支无任何新提交与未提交改动
  - [ ] 同一仓库两个 Issue 并发触发两条工作流时，两条工作流各自持有独立副本，产物互不覆盖

#### 功能点 2: 工作区主分支自动识别与回填

- **描述**: 当工作区尚未记录主分支信息时，系统在建立隔离前自动识别主分支并记录到工作区：GitHub 项目优先通过平台 GitHub 授权获取仓库主分支；获取不到或不是 GitHub 项目时，按 main → master → release 的顺序探测本地仓库，以第一个存在的分支为准。识别成功后该信息对工作区持久生效（后续触发、手工实例化均直接复用，不重复探测）。
- **用户价值**: 彻底免除「手工设置主分支」这一隐形成本；联动链路全程无人工介入也能可靠隔离；同时修复平台内既有「主分支信息缺失即无法实例化」的历史问题。
- **验收标准**:
  - [ ] GitHub 项目工作区主分支信息缺失时，自动获取仓库主分支并记录，随后正常建立隔离
  - [ ] 非 GitHub 项目（或获取失败）时，按 main → master → release 顺序探测到第一个存在的分支并记录
  - [ ] 回填后主分支信息在工作区详情中可见，后续实例化不再重复探测
  - [ ] 手工实例化遇到主分支信息缺失时同样自动识别，不再直接报错失败

#### 功能点 3: 隔离确实无法建立时明确失败

- **描述**: 仅当主分支完全无法识别（非 Git 仓库，或候选分支均不存在），或隔离副本建立本身失败时，本次触发以失败终态结束，并记录人类可读的失败原因；**不允许**静默降级为在主分支上执行。
- **用户价值**: 失败可感知、可定位、可重试，避免「以为在隔离环境、实际改了主分支」的最差结果。
- **验收标准**:
  - [ ] 主分支无法识别或隔离副本建立失败时，该次触发记录为失败状态，原因清晰可读
  - [ ] 失败后工作区主分支无任何由本次触发产生的改动
  - [ ] 修复前置条件（如完成仓库初始化）后重新触发同一 Issue，可正常识别主分支、建立隔离并执行

#### 功能点 4: 既有入口行为保持

- **描述**: 本次修复不改变 Issues 联动配置的维护方式与平台内手工实例化的隔离选项（勾选与否）语义；已按节点单独配置隔离的工作流，其节点级隔离行为不变。
- **用户价值**: 修复范围可控，老用户既有习惯与配置不受任何影响。
- **验收标准**:
  - [ ] 手工实例化时勾选/不勾选「为工作流创建独立 Worktree」的行为与修复前完全一致
  - [ ] 节点级已配置隔离的工作流，经联动触发时节点级隔离仍然生效

### 3.3 用户操作流程

```mermaid
flowchart TD
    A[为 Issue 打上联动标签] --> B[自动完成工作区准备]
    B --> C{工作区已记录主分支?}
    C -->|已记录| E[创建独立 Worktree 副本与分支]
    C -->|未记录| D{自动识别主分支<br/>GitHub 项目优先经授权获取<br/>否则按 main→master→release 探测}
    D -->|识别成功并记录| E
    D -->|完全无法识别| H[本次触发标记失败]
    E --> F[实例化工作流，所有节点在副本中执行]
    F --> G[Issue 回评工作流地址]
    G --> I[首个人类节点自动完成，工作流继续流转]
    H --> J[平台中可查看失败原因]
    J --> K[修复前置条件后重新触发]
    K --> B
```

### 3.4 页面/界面描述

本需求不新增配置入口与页面。既有界面中的表现要求：

| 页面 | 描述 | 关键元素 |
|------|------|---------|
| 工作流实例详情 | 联动触发的实例与手工勾选隔离的实例一样，可看到独立副本/分支信息 | 实例的 Worktree 分支信息 |
| 工作区详情 | 自动识别回填的主分支信息可见，与手工设置的主分支展示一致 | 工作区主分支 |
| 云电脑设置「Github」区块 | 联动配置列表维护方式不变，无新增选项 | 维持现状 |
| Issue 评论区 | 回评行为不变：告知工作流已触发并附查看地址 | 工作流查看地址 |

### 3.5 异常与边界情况

| 情况 | 预期行为 |
|------|---------|
| 工作区未记录主分支，但为 GitHub 项目 | 自动获取仓库主分支并记录，继续建立隔离 |
| 工作区未记录主分支，非 GitHub 项目或获取失败 | 按 main → master → release 顺序探测，以第一个存在的分支为准并记录 |
| 非 Git 仓库或候选分支均不存在 | 本次触发明确失败，原因可读，主分支零改动 |
| 隔离副本建立本身失败（如控制器异常） | 本次触发明确失败，原因可读，主分支零改动 |
| 同一 Issue 重复打标/事件重复投递 | 仍只触发一次（维持既有幂等行为），不会重复建副本 |
| 多条联动配置命中同一 Issue | 每条配置各触发一条工作流，各自持有独立副本 |
| 隔离副本已建立但实例创建中途失败 | 已建立的副本被清理，不留垃圾 |
| 工作流实例被删除 | 其独立副本随之清理（维持既有清理行为） |
| 手工实例化（非联动） | 隔离选项语义不变；主分支缺失时同样自动识别，不直接失败 |

## 四、非功能需求

### 4.1 性能要求

- 主分支自动识别仅在工作区缺失该信息时发生，且识别结果持久复用；建立隔离副本不应显著拉长「打标签 → 工作流启动」的端到端耗时，整体仍维持在秒级到分钟级的既有水平。

### 4.2 安全性要求

- 联动触发的工作流任何情况下不得直接在工作区主分支上执行；这是本需求的硬约束。
- GitHub 项目主分支识别复用平台既有 GitHub 授权与最小化凭据体系，不引入新的授权范围。

### 4.3 兼容性要求

- 已存在的联动配置无需修改即自动获得隔离行为；
- 已记录主分支信息的工作区行为完全不变（直接复用，不重新识别）；
- 修复前已在执行中的存量工作流实例不受影响，按原方式执行完毕。

## 五、依赖与约束

### 5.1 依赖

- 云电脑 GitHub Issues 联动能力（见 [[20261025-github-issues-workflow]]）；
- 工作流实例的独立 Worktree 能力（见 [[20260817-session-lifecycle-and-worktree-management]]、[[20260829-workflow-worktree-session-start]]）；
- GitHub 帐号绑定与仓库授权（见 [[20260709-github-account-binding]]）。

### 5.2 约束

- 不改变联动配置的数据结构与维护方式；
- 不改变手工实例化入口的隔离选项语义；
- 触发链路保持「事件不等待全链路」的异步推进方式；
- 主分支自动识别的候选顺序固定为 main → master → release，存在的优先。
